# AGENTS.md — working on `amplifier-bundle-claim-guard`

Guidance for coding agents (and humans) working in **this repo**. Read it before you
change, test, or explore anything here.

**What this repo is:** `claim-guard` is an Amplifier bundle that runs an **adversarial
claim-verification gate** over a changeset. For every claim a change makes (commit
messages, docstrings, spec/design docs, implicit purpose) it tries to prove that claim
**false against the actual shipped source**, then BLOCKs merge on any REFUTED claim or any
safety claim with no adverse-state test. The user-facing overview is in `README.md`; this
file is the *builder's* map.

## Install shapes — the load-bearing contract (do not break)

`claim-guard` is meant to **layer onto** the bundle you already run. **You `--app` the
BEHAVIOR; `bundle.md` is a thin wrapper.** Each behavior is **self-sufficient** — it
includes the `modes`/`recipes`/`lsp` (and, for probing, the DTU/parallax/tester) *behaviors*
it needs, so layering it composes the whole gate on its own.

| Shape | Command | Composes |
|---|---|---|
| **Behavior `--app`** (recommended) | `amplifier bundle add "git+https://github.com/colombod/amplifier-bundle-claim-guard@main#subdirectory=behaviors/claim-guard.yaml" --app` | 7 agents + `claim_ledger` + `/claim-guard` mode + mode/recipes/lsp tools |
| **Full/Phase-2 behavior `--app`** | `amplifier bundle add "git+…@main#subdirectory=behaviors/claim-guard-probing.yaml" --app` | 10 agents + delegatable DTU/parallax/amplifier-tester primitives |
| **Root bundle standalone** | `amplifier bundle add git+…@main` then `amplifier bundle use claim-guard` | Same as behavior `--app`, as a dedicated session |

**Invariant a behavior must always satisfy:** layering it via `--app` must compose the
**whole** capability with **no root bundle required**. A behavior that is *not*
self-sufficient composes an empty/partial surface under `--app` **with no error** — silent
failure. If you touch a `behaviors/*.yaml`, re-prove composition (see "Explore / verify
composition" below) before you call it done.

**Never `--app` the root `bundle.md`** — it drags foundation into a session that already
has it. The root is for `bundle use` only.

**Wiring rules that bite silently:**
- Module/skill `source:` values are **pinned git URLs** (`…@main#subdirectory=…`), never
  relative paths — a relative source re-bases onto another bundle's cache dir under registry
  composition and breaks.
- Mode `search_paths` uses the **root** namespace `@claim-guard:modes` (repo root, where
  `modes/` lives), not `@claim-guard-behavior:modes` (which resolves to `behaviors/`).

## Testing

Two independent layers. **CI gates one; you run the other locally.**

### 1. Module tests + lint + harness (CI-gated — mirror these exactly)

The `.github/workflows/ci.yml` check **`tool-claim-ledger tests + harness selftest + lint`**
is the required status check on `main`. Reproduce it verbatim before pushing:

```bash
cd modules/tool-claim-ledger
uv venv
# amplifier_core is a PEER dep (host provides it at runtime); the module does NOT declare it,
# so install it explicitly from the canonical source. NOTE: amplifier-core's pyproject is at
# its repo ROOT — NO #subdirectory fragment.
uv pip install --python .venv -e . pytest pytest-asyncio \
  "amplifier-core @ git+https://github.com/microsoft/amplifier-core@main"
.venv/bin/python -m pytest tests/ -q            # the ledger test suite

# Lint — ruff is PINNED to match CI (an unpinned `uvx ruff` pulls latest and can fail on
# newly-enabled rules CI didn't see). Same version everywhere:
uvx ruff@0.16.3 format --check amplifier_module_tool_claim_ledger tests
uvx ruff@0.16.3 check         amplifier_module_tool_claim_ledger tests

# From the repo root, the harness (lint + selftest):
cd ..
uvx ruff@0.16.3 format --check scripts/harvest_stability.py
uvx ruff@0.16.3 check         scripts/harvest_stability.py
modules/tool-claim-ledger/.venv/bin/python scripts/harvest_stability.py --selftest
```

- Run against **`.venv/bin/python`**, not `uv run` — `uv run` re-syncs to the module's own
  project env (`dependencies = []`) and drops `amplifier_core` → `ModuleNotFoundError`.
- There is **no Makefile**; the commands above are the interface.
- `python_check` (ruff/pyright) is a fine fast pre-check while iterating, but the pinned
  `ruff@0.16.3` above is what CI enforces.

### 2. DTU advertisement smoke — **run LOCALLY, not in CI**

`dtu/profiles/*.yaml` are Digital Twin Universe profiles that prove — in a clean isolated
container — that installing the bundle from `@main` actually **composes and advertises its
contributions** for each install shape (behavior `--app` vs root bundle vs probing). They are
**composition/advertisement** tests: **no `pytest`, no module unit tests.** They are
**intentionally NOT wired into GitHub Actions** — DTU needs Incus + an `ANTHROPIC_API_KEY` and
is run on a developer machine.

Run one (full steps + the requirement notes are in **`dtu/README.md`**):

```bash
amplifier-digital-twin launch dtu/profiles/claim-guard-behavior-app.yaml --name cg-shapeA
amplifier-digital-twin check-readiness cg-shapeA          # -> ready:true  == PASS (self-proving)
amplifier-digital-twin exec cg-shapeA -- cat /root/advertisement.txt   # human-readable evidence
amplifier-digital-twin destroy cg-shapeA
```

Each profile self-proves: it runs the advertisement probe once and a `readiness` grep asserts
the expected agents/tool/mode — so `ready:true` **is** the PASS. **Run these locally when you
change any `behaviors/*.yaml`, `bundle.md`, `bundles/*.yaml`, agent roster, mode, or skill
wiring** — i.e. anything that changes what the install advertises. The module test suite will
NOT catch an install-shape regression; only these will.

## Explore / verify composition (no DTU needed)

To check what a shape composes on your host, install it and ask a one-shot session to
enumerate its own surface. **Always start from a clean registry state** — a stale
`bundle.app`/`bundle.added` entry produces confusing empty/partial results:

```bash
amplifier bundle remove claim-guard 2>/dev/null; amplifier bundle remove claim-guard-behavior 2>/dev/null
grep -n claim-guard ~/.amplifier/settings.yaml || echo "clean"      # confirm both bundle.added AND bundle.app are clear

amplifier bundle add "git+https://github.com/colombod/amplifier-bundle-claim-guard@main#subdirectory=behaviors/claim-guard.yaml" --app
amplifier run -B foundation --mode single \
  "List, do not read code: claim-guard:* sub-agents; whether claim_ledger is available and its op count; whether the /claim-guard mode is available; whether mode/recipes/lsp tools are present."
```

Expect: 7 `claim-guard:*` agents, `claim_ledger` (15 ops), `/claim-guard` mode (inert),
mode+recipes+lsp tools. The **root-bundle** shape must advertise the **identical** set — that
equivalence is the proof the behavior is self-sufficient.

**Do all work from this checkout, never from `~/.amplifier/cache/…`** (that's managed
infrastructure, overwritten on cache update). When testing a not-yet-merged change, `--app`
the **branch ref** (`@<branch>#subdirectory=…`) instead of `@main`.

## The `claim_ledger` tool — hands off the storage

The ledger's on-disk shape (under `.claim-guard/<run-id>/`) is **private to the tool**.
**Never read or write `.claim-guard/` directly** (no `read_file`/`cat`/`jq`) — inspect it only
through the tool (`claim_ledger list_claims` / `report`). Every interaction going through the
tool is what makes a run's context un-fudgeable. The authoritative interface is
`docs/tool-claim-ledger-contract.md`. Structural gate rule: a `CONFIRMED`/`REFUTED` verdict
requires a `file:line` anchor, and a `REFUTED` can only be cleared by **new evidence**, never
by prose.

## Contribution workflow — `main` is PR-protected

`main` requires a pull request; direct pushes are blocked (branch protection with
`enforce_admins: true`), the CI check must pass, and force-pushes/deletions are disallowed.
0 approvals are required (solo-maintainer), so you self-merge once CI is green.

```bash
git checkout -b <type>/<short-desc>      # feat/ fix/ docs/ test/ chore/
# … make the change; run the CI-mirrored tests above; run the DTU smoke if wiring changed …
git push -u origin <branch>
gh pr create --repo colombod/amplifier-bundle-claim-guard --base main --head <branch> --title "…" --body "…"
gh pr checks <n> --repo colombod/amplifier-bundle-claim-guard   # wait for pass
gh pr merge  <n> --repo colombod/amplifier-bundle-claim-guard --squash --delete-branch
```

- **Commit identity:** author as `colombod <colombod@me.com>`; use the `gh` session
  authenticated as `colombod`.
- After merging a wiring change, tell users to `amplifier bundle remove claim-guard*` and
  re-add — a running session has the old composition in memory.
- If you touched `bundle.md`/`behaviors/`/`agents/`/`modes/`/`skills/`, run
  `validate-bundle-repo` (it regenerates a stale `bundle.dot`/`bundle.png`).
